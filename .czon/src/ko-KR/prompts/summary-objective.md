# 객관적 중립 스타일 분석 보고서

## 읽기 포커스 포인트

각 파일을 읽을 때 다음을 중점적으로 추출하세요:

- 파일 경로와 제목
- 날짜 정보
- 관련된 프로젝트 이름과 기능 설명
- 언급된 인물 및 그 역할
- 객관적 사실과 데이터
- 버전 번호, 마일스톤 등 구체적 정보

**무시할 사항**: 주관적 평가, 감정 표현, 추측성 내용

## 지식베이스 구조

```
### 파일 인덱스
| 파일 경로 | 제목 | 날짜 |
|----------|------|------|

### 프로젝트 인덱스
| 프로젝트명 | 설명 | 관련 파일 |
|--------|------|----------|

### 인물 인덱스
| 인물 | 역할 | 관련 파일 |
|------|------|----------|

### 타임라인
| 날짜 | 사건 | 출처 파일 |
|------|------|----------|

### 이론/프레임워크 인덱스
| 이름 | 핵심 아이디어 | 출처 파일 |
|------|----------|----------|
```

## 압축 전략

지식베이스를 압축해야 할 때:

1. **반드시 유지**: 파일 인덱스(경로+제목), 프로젝트 인덱스, 인물 인덱스
2. **간소화 가능**: 타임라인(핵심 노드 유지), 이론 인덱스(이름과 출처 유지)
3. **삭제 가능**: 상세 설명, 부차적 사건

## 스타일 포지셔닝

객관적 중립의 관점에서 내용을 소개하고, 주관적 평가와 감정적 색채를 피하세요. 사실과 데이터를 강조하여 정보의 정확성과 신뢰성을 보장하세요.

**대상 독자**: 저장소 전체를 빠르게 파악해야 하는 새로운 독자, 잠재적 협력자, 투자자
**작성 어조**: 전문적, 절제된, 중립적, 이력서나 경력기술서를 작성하는 것처럼
**목적**: 독자가 내용의 기본 정보와 핵심 관점을 포괄적으로 이해하고 스스로 판단을 형성하도록 돕기

## 금지 사항

- ❌ 감정 표현 추가 금지 (예: "고무적인", "유감스럽게도")
- ❌ 추측 금지 (예: "아마도", "어쩌면", "대략")
- ❌ 주관적 평가 어휘 사용 금지 (예: "우수한", "형편없는", "흥미로운")
- ❌ 좋고 나쁨 평가 금지
- ❌ 1인칭 사용 금지

## 필수 섹션 구조

### 개요

- 저장소 소유자 소개 (이름/ID, 신원, 주요 분야)
- 저장소 내용의 시간 범위
- 주요 프로젝트 목록 (간단히 열거)

### 프로젝트 소개

각 주요 프로젝트에 대해 다음 구조를 사용하세요:

```markdown
### [프로젝트 이름]

- **기원**: 프로젝트의 출처와 배경
- **핵심 기능**:
  - 기능 포인트 1
  - 기능 포인트 2
- **버전 반복**: 버전 기록이 있다면 간략히 설명
- **관련 파일**: [글 제목](../path/to/file.md)
```

### 주요 주제

주제별로 내용을 분류 정리하세요:

```markdown
### 1. [주제 이름]

- [글 제목1](../path/to/file1.md): 핵심 관점 요약
- [글 제목2](../path/to/file2.md): 핵심 관점 요약
```

### 타임라인

표 형식을 사용하여 핵심 사건을 표시하세요:

```markdown
| 날짜       | 핵심 사건             |
| ---------- | -------------------- |
| YYYY-MM-DD | 사건 설명 (객관적 서술) |
```

### 주요 인물

표 형식을 사용하세요:

```markdown
| 인물    | 역할      | 비고         |
| ------- | --------- | ------------ |
| 이름/ID | 직위/관계 | 관련 객관적 정보 |
```

### 이론 프레임워크 요약

저장소에서 제시된 이론/프레임워크에 대해:

```markdown
### [프레임워크 이름]

- **핵심 아이디어**: 한 문장으로 요약
- **핵심 요소**: 핵심 구성 요소 열거
- **수학적 표현**: 공식이 있다면 나열
```
